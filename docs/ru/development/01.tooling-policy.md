# Политика инструментов проекта

Документ объясняет, какие инструменты используются в проекте, почему выбран каждый из них и как они сочетаются. Служит источником истины при спорных вопросах и точкой входа для новых участников.

Связанные документы:
- [Управление Node.js и pnpm через mise](./mise-pnpm-node-setup.md)
- [pnpm в TypeScript-проекте](./pnpm-typescript.md)

## 1. Краткая сводка

| Инструмент / механизм | Используем? | Роль |
|---|---|---|
| `mise` + `.mise.toml` | **Да** | Единственный источник версий Node.js, pnpm и других инструментов |
| `pnpm` | **Да** | Менеджер пакетов проекта |
| `packageManager` в `package.json` | **Да** | Метаданные: документируют ожидаемую версию pnpm для CI и внешних инструментов |
| `corepack enable` | **Нет** | Конфликтует с `mise` за управление версией pnpm |
| `npm` | **Нет** | Заменён на `pnpm` |
| `yarn` | **Нет** | Заменён на `pnpm` |
| `nvm`, `fnm`, `volta` | **Нет** | Заменены на `mise` |

## 2. Почему `mise`

`mise` — менеджер версий инструментов и задач. В нашем проекте он отвечает за:

- установку и активацию нужной версии Node.js;
- установку и активацию нужной версии `pnpm`;
- установку прочих CLI-инструментов (например, `pi`);
- определение стандартных задач (`mise run build` и т. п.).

### Причины выбора

1. **Единый источник версий.** Все версии фиксируются в одном файле `.mise.toml` в корне репозитория.
2. **Воспроизводимость.** Любой разработчик, клонировав репозиторий и запустив `mise install`, получает идентичное окружение.
3. **Не только Node.js.** `mise` управляет любыми инструментами, а не только Node.js. Это важно, если в проекте появляются, например, `terraform`, `kubectl` или собственные CLI.
4. **Активация по директории.** При входе в каталог проекта версии подхватываются автоматически.
5. **Простая интеграция с CI.** Официальный `jdx/mise-action` устанавливает всё нужное одной строкой.

### Альтернативы и почему не они

- **`nvm` / `fnm`** — управляют только Node.js. Для pnpm и других инструментов требуются отдельные решения.
- **`volta`** — управляет Node.js и пакетными менеджерами, но хуже расширяется на произвольные CLI.
- **Ручная установка** — не воспроизводимо.

## 3. Почему `pnpm`

`pnpm` — менеджер пакетов для Node.js. В проекте используется именно он.

### Причины выбора

1. **Экономия дискового пространства.** Пакеты хранятся в глобальном store и связываются через hard links.
2. **Строгая изоляция зависимостей.** `node_modules` содержит только объявленные зависимости, что устраняет «фантомные» импорты.
3. **Скорость.** Быстрее `npm` и `yarn` за счёт кэша и параллельной загрузки.
4. **Workspaces из коробки.** Не нужны сторонние решения для монорепозиториев.
5. **Совместимость.** Работает с любыми пакетами из npm-реестра.

### Альтернативы и почему не они

- **`npm`** — медленнее, слабее изоляция зависимостей, хуже работает с монорепозиториями.
- **`yarn` (v1)** — legacy. `yarn berry` (v2+) имеет собственные сложности (PnP, zero-installs), которые не оправданы в нашем контексте.

## 4. Почему `packageManager` в `package.json` — да, а `corepack enable` — нет

Это самое частое место путаницы. Разберём по частям.

### `packageManager` в `package.json`

```json
{
  "packageManager": "pnpm@12.11.2"
}
```

Это **метаданные**. Поле читают:

- CI-системы и боты (например, Renovate) — чтобы понять, какой пакетный менеджер ожидается;
- `pnpm` при запуске — для самоидентификации;
- `corepack` — но только если он активирован.

Само по себе поле ничего не активирует и ни с чем не конфликтует. **Мы его используем** — как документацию ожидаемой версии `pnpm`.

### `corepack enable`

`corepack` — это встроенный в Node.js механизм, который устанавливает шимы `pnpm` и `yarn` в `PATH`. При вызове `pnpm` шим читает `packageManager` из `package.json` и подменяет бинарь на нужную версию.

Проблема в том, что **`mise` делает то же самое**: устанавливает `pnpm` нужной версии и кладёт его в `PATH`. Две системы начинают конкурировать за управление одной и той же командой. Итоговое поведение зависит от порядка `PATH` и может различаться между машинами, что ломает воспроизводимость.

**Правило проекта:** `corepack enable` не используем. Версия `pnpm` управляется только через `mise`.

### Итого

| Действие | Разрешено? | Почему |
|---|---|---|
| Указать `packageManager` в `package.json` | Да | Метаданные, безопасно |
| Запустить `corepack enable` | Нет | Конфликтует с `mise` |
| Установить pnpm через `corepack prepare` | Нет | Дублирует `mise` |

## 5. Как инструменты сочетаются

Порядок работы при входе в директорию проекта:

1. Оболочка вызывает `mise` (через shell-хук, установленный при `mise activate`).
2. `mise` читает `.mise.toml` и добавляет в `PATH` нужные версии Node.js и `pnpm`.
3. `node` и `pnpm` в текущей сессии указывают на версии из `.mise.toml`.
4. `pnpm install` использует `pnpm-lock.yaml` для воспроизводимой установки зависимостей.
5. В `package.json` поле `packageManager` документирует ту же версию `pnpm` для CI и внешних инструментов.

Схематично:

```
.mise.toml          →  mise  →  PATH  →  node, pnpm
package.json        →  packageManager  →  CI, Renovate, pnpm (self-check)
pnpm-lock.yaml      →  pnpm install    →  node_modules
```

## 6. Правила для участников

1. **Не устанавливайте `pnpm` глобально** через `npm i -g pnpm` или `brew install pnpm`. Версия должна приходить из `mise`.
2. **Не запускайте `corepack enable`.**
3. **Не используйте `npm` или `yarn`** для установки зависимостей. Только `pnpm`.
4. **Коммитьте `pnpm-lock.yaml`** — это часть репозитория.
5. **При обновлении версии `pnpm`** меняйте её в двух местах: `.mise.toml` и `packageManager` в `package.json`. Держите их синхронными.
6. **При обновлении версии Node.js** меняйте её в `.mise.toml` и, при необходимости, в `engines.node` в `package.json`.
7. **После обновления Node.js или `pnpm`** переустанавливайте зависимости: `rm -rf node_modules && pnpm install`.

## 7. Как обновлять версии

### pnpm

```bash
mise latest pnpm
mise use pnpm@<version>
```

Затем вручную обновите `packageManager` в `package.json` до той же версии.

### Node.js

```bash
mise use node@<version>
```

При необходимости обновите `engines.node` в `package.json`.

### Проверка актуальности

```bash
mise outdated --bump
pnpm outdated
```

## 8. CI

В CI используется `jdx/mise-action`, который читает `.mise.toml` и устанавливает всё нужное. `corepack` не активируется.

Минимальный workflow:

```yaml
- uses: jdx/mise-action@v2
  with:
    install: true
- run: pnpm install --frozen-lockfile --ignore-scripts
```

`--frozen-lockfile` гарантирует, что CI не изменит `pnpm-lock.yaml`, а `--ignore-scripts` — что не будут выполнены посторонние `postinstall`-скрипты.
