# pnpm в TypeScript-проекте

Документ описывает, как использовать `pnpm` в TypeScript-проекте, где версии инструментов управляются через `mise`.

Связанные документы:
- [Политика инструментов проекта](./01.tooling-policy.md) — почему именно `mise` и `pnpm`
- [Управление Node.js и pnpm через mise](./02.mise-pnpm-node-setup.md) — команды установки и обновления

## 1. Почему pnpm

`pnpm` — быстрый и эффективный менеджер пакетов для Node.js. Ключевые преимущества:

- **Экономия дискового пространства** — пакеты хранятся в глобальном хранилище и связываются через hard links.
- **Строгая изоляция зависимостей** — `node_modules` содержит только то, что объявлено в `package.json`, что устраняет «фантомные» зависимости.
- **Быстрая установка** — за счёт кэша и параллельной загрузки.
- **Поддержка workspaces** — встроенная работа с монорепозиториями.
- **Совместимость с npm-реестром** — работает с любыми пакетами из npm.

## 2. Предварительные требования

- `mise` установлен и настроен.
- `pnpm` добавлен в `.mise.toml` (см. [02.mise-pnpm-node-setup.md](./02.mise-pnpm-node-setup.md)).
- Node.js версии 24.x.

Проверка окружения:

```bash
mise current node pnpm
node -v
pnpm -v
```

## 3. Инициализация проекта

### 3.1. Создание package.json

```bash
pnpm init
```

### 3.2. Фиксация версии pnpm

Добавьте в `package.json` поле `packageManager` и ограничение на Node.js:

```json
{
  "name": "my-ts-project",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "packageManager": "pnpm@12.11.2",
  "engines": {
    "node": ">=24"
  }
}
```

Поле `packageManager` — это метаданные для CI и Renovate. Фактическую версию `pnpm` задаёт `mise` (см. [02.mise-pnpm-node-setup.md](./02.mise-pnpm-node-setup.md)).

> **Не используйте `corepack enable`.** Причины описаны в [Политике инструментов](./01.tooling-policy.md).

Убедитесь, что версии в `packageManager` и `.mise.toml` совпадают. При обновлении `pnpm` через `mise` обновляйте оба места.

### 3.3. Настройка `.npmrc`

Создайте `.npmrc` в корне проекта:

```ini
# Использовать строгий режим peer-зависимостей
strict-peer-dependencies=true

# Автоматически устанавливать peer-зависимости
auto-install-peers=true

# Не использовать hoisting (pnpm использует изолированную структуру)
shamefully-hoist=false

# Точные версии в lockfile
resolution-mode=highest
```

> Для большинства проектов достаточно значений по умолчанию. Меняйте параметры осознанно.

## 4. Установка TypeScript и зависимостей

### 4.1. Базовые dev-зависимости

```bash
pnpm add -D typescript @tsconfig/strictest @tsconfig/node24
```

- `typescript` — компилятор.
- `@tsconfig/strictest` — строгий пресет с максимальными проверками.
- `@tsconfig/node24` — пресет для Node.js 24.

### 4.2. Раннер для разработки

```bash
pnpm add -D tsx
```

`tsx` позволяет запускать TypeScript напрямую без предварительной компиляции — удобно для dev-режима.

### 4.3. Тестирование

```bash
pnpm add -D vitest
```

### 4.4. Линтинг и форматирование

```bash
pnpm add -D @biomejs/biome
```

Biome — быстрый линтер и форматтер, заменяющий ESLint + Prettier.

## 5. Структура проекта

```
my-ts-project/
├── .mise.toml
├── .npmrc
├── package.json
├── pnpm-lock.yaml
├── tsconfig.json
├── biome.json
├── src/
│   └── index.ts
├── tests/
│   └── index.test.ts
└── dist/              # генерируется при сборке
```

## 6. Конфигурация TypeScript

Файл `tsconfig.json`:

```json
{
  "extends": [
    "@tsconfig/strictest/tsconfig.json",
    "@tsconfig/node24/tsconfig.json"
  ],
  "compilerOptions": {
    "outDir": "dist",
    "rootDir": "src",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "target": "ES2023",
    "sourceMap": true,
    "declaration": true,
    "declarationMap": true,
    "noEmitOnError": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}
```

## 7. Скрипты в package.json

Добавьте в `package.json`:

```json
{
  "scripts": {
    "build": "tsc",
    "dev": "tsx watch src/index.ts",
    "start": "node dist/index.js",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:watch": "vitest",
    "lint": "biome check .",
    "lint:fix": "biome check --write .",
    "format": "biome format --write .",
    "clean": "rm -rf dist node_modules"
  }
}
```

Запуск:

```bash
pnpm build
pnpm dev
pnpm test
pnpm lint
```

## 8. Работа с workspace (монорепозиторий)

`pnpm` поддерживает workspaces из коробки. Создайте файл `pnpm-workspace.yaml`:

```yaml
packages:
  - "packages/*"
  - "apps/*"
```

Структура монорепозитория:

```
my-monorepo/
├── pnpm-workspace.yaml
├── package.json
├── packages/
│   ├── shared/
│   │   ├── package.json
│   │   └── src/
│   └── utils/
│       ├── package.json
│       └── src/
└── apps/
    └── api/
        ├── package.json
        └── src/
```

В корневом `package.json`:

```json
{
  "name": "my-monorepo",
  "private": true,
  "scripts": {
    "build": "pnpm -r build",
    "test": "pnpm -r test",
    "lint": "pnpm -r lint"
  }
}
```

Установка зависимостей во всех пакетах:

```bash
pnpm install
```

Добавление зависимости в конкретный пакет:

```bash
pnpm add lodash --filter @my/shared
```

Ссылка между пакетами (workspace-протокол):

```json
{
  "dependencies": {
    "@my/shared": "workspace:*"
  }
}
```

## 9. Полезные команды pnpm

### Установка

```bash
pnpm install                # установить все зависимости
pnpm install --frozen-lockfile  # для CI: строго по lockfile
pnpm install --ignore-scripts   # не запускать postinstall-скрипты
```

### Добавление и удаление

```bash
pnpm add lodash             # в dependencies
pnpm add -D vitest          # в devDependencies
pnpm add -O lodash          # в optionalDependencies
pnpm remove lodash          # удалить
pnpm update                 # обновить в рамках semver
pnpm update --latest        # обновить до последних версий
```

### Просмотр

```bash
pnpm list                   # список зависимостей
pnpm list --depth 0         # только прямые
pnpm why lodash             # почему установлен пакет
pnpm outdated               # устаревшие зависимости
pnpm audit                  # проверка уязвимостей
```

### Запуск скриптов

```bash
pnpm run build              # запустить скрипт
pnpm build                  # короткая форма
pnpm exec tsc --version     # запустить бинарь из node_modules
pnpm dlx create-vite        # запустить пакет без установки
```

## 10. CI/CD

### GitHub Actions

Пример workflow `.github/workflows/ci.yml`:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: jdx/mise-action@v2
        with:
          install: true

      - name: Install dependencies
        run: pnpm install --frozen-lockfile --ignore-scripts

      - name: Typecheck
        run: pnpm typecheck

      - name: Lint
        run: pnpm lint

      - name: Test
        run: pnpm test

      - name: Build
        run: pnpm build
```

`jdx/mise-action` автоматически установит версии Node.js и pnpm, зафиксированные в `.mise.toml`.

### Кэширование pnpm store

В CI полезно кэшировать глобальный store `pnpm`:

```yaml
      - name: Get pnpm store directory
        shell: bash
        run: echo "STORE_PATH=$(pnpm store path --silent)" >> $GITHUB_ENV

      - uses: actions/cache@v4
        with:
          path: ${{ env.STORE_PATH }}
          key: ${{ runner.os }}-pnpm-store-${{ hashFiles('**/pnpm-lock.yaml') }}
          restore-keys: |
            ${{ runner.os }}-pnpm-store-
```

## 11. Best practices

1. **Всегда коммитьте `pnpm-lock.yaml`.** Это обеспечивает воспроизводимость установки.
2. **Используйте `--frozen-lockfile` в CI.** Запрещает изменение lockfile во время сборки.
3. **Не смешивайте пакетные менеджеры.** Если проект на `pnpm`, не запускайте `npm install` или `yarn`.
4. **Фиксируйте версию pnpm** через `packageManager` в `package.json` или через `.mise.toml`.
5. **Не используйте `shamefully-hoist=true`** без необходимости — это ломает изоляцию зависимостей.
6. **Проверяйте `pnpm outdated`** регулярно и обновляйте зависимости осознанно.
7. **Используйте `pnpm dlx`** для одноразового запуска пакетов вместо глобальной установки.
8. **Настраивайте `.npmrc`** под нужды проекта, но не копируйте чужие конфиги слепо.
9. **Храните `node_modules` вне git** — добавьте в `.gitignore`.

Пример `.gitignore`:

```gitignore
node_modules/
dist/
*.log
.DS_Store
.env
.env.local
coverage/
```
