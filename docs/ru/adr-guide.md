# Руководство по Architecture Decision Records

## Обзор

Проект использует MADR (Markdown Architectural Decision Records) версии 4.0.0 для документирования значимых решений. ADR фиксируют контекст, рассмотренные варианты и обоснование каждого выбора.

## Зачем нужны ADR

- Будущие участники понимают, почему приняты решения.
- Решения можно пересмотреть с полным контекстом.
- Эволюция проекта становится прозрачной.
- Альтернативы сохраняются, а не теряются.

## Формат

Каждый ADR — Markdown-файл в `docs/decisions/` с паттерном именования:

```
NNNN-title-with-dashes.md
```

Где `NNNN` — последовательный номер, начиная с `0001`.

## Шаблон

```markdown
---
status: "accepted"
date: "YYYY-MM-DD"
decision-makers: ["ваше-имя"]
---

# Короткое название решения

## Контекст и формулировка проблемы

Опишите контекст и проблему. Используйте два-три предложения.
Сформулируйте проблему как вопрос, если возможно.

## Факторы решения

* {фактор или preocupación, влияющий на решение}
* {другой фактор}

## Рассмотренные варианты

* {название варианта 1}
* {название варианта 2}
* {название варианта 3}

## Итоговое решение

Выбранный вариант: "{название варианта 1}", потому что {обоснование}.

### Последствия

* Хорошо, потому что {положительное последствие}
* Плохо, потому что {отрицательное последствие}

### Подтверждение

{Как проверить, что решение всё ещё актуально.}

## Плюсы и минусы вариантов

### {название варианта 1}

* Хорошо, потому что {аргумент a}
* Хорошо, потому что {аргумент b}
* Плохо, потому что {аргумент c}

### {название варианта 2}

* Хорошо, потому что {аргумент a}
* Плохо, потому что {аргумент b}
```

## Правила написания

### Делать

- Пишите один ADR на одно решение.
- Держите заголовок коротким и описательным.
- Используйте активный залог.
- Формулируйте проблему до решения.
- Перечисляйте все серьёзные варианты, не только победителя.
- Включайте отрицательные последствия.
- Ссылайтесь на связанные ADR при необходимости.

### Не делать

- Не пишите детали реализации.
- Не дублируйте информацию из README или документации.
- Не пишите ADR для тривиальных выборов.
- Не изменяйте принятые ADR — пишите новые, которые их заменяют.

## Значения статуса

| Статус | Значение |
|--------|----------|
| `proposed` | На обсуждении, ещё не финальное |
| `accepted` | Решение активно |
| `deprecated` | Больше не актуально, но не заменено |
| `superseded by ADR-NNNN` | Заменено более поздним решением |

## Процесс

1. Скопируйте шаблон в `docs/decisions/NNNN-title.md`.
2. Заполните все секции.
3. Установите `status: proposed`.
4. Закоммитьте с сообщением: `docs(adr): propose NNNN-title`.
5. После ревью измените на `status: accepted`.
6. Закоммитьте с сообщением: `docs(adr): accept NNNN-title`.

## Замена решения

Когда решение меняется:

1. Напишите новый ADR с новым решением.
2. В старом ADR измените статус на `superseded by ADR-NNNN`.
3. Добавьте ссылку из нового ADR на старый.
4. Не удаляйте и не переписывайте старый ADR.
